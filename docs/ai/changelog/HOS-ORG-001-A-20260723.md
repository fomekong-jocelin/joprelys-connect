- création du bounded context `hospitalorganization`, distinct de `spatial` ;
- hiérarchie organisationnelle facultative `POLE → DEPARTMENT → SERVICE → CARE_UNIT` ;
- création directe d'un service sous l'établissement pour les petites structures ;
- catalogue codifié et bilingue des services hospitaliers ;
- catalogue codifié et bilingue des spécialités médicales ;
- service identifié en base par `serviceCatalogCode`, sans libellé français ou anglais figé dans `organizational_units` ;
- désactivation/réactivation des unités au lieu d'une suppression destructive ;
- permission dédiée `ORGANIZATION_STRUCTURE_MANAGE` ;
- isolation tenant par scope authentifié, `@TenantId`, repositories explicitement filtrés et FK composites ;
- API `/api/hospital-organization` ;
- écran Angular mobile-first, responsive, light/dark et FR/EN ;
- route et navigation permission-first ;
- erreurs API localisées ;
- Flyway V87 avec référentiels services, spécialités et types d'unités ;
- tests H2, PostgreSQL 16, MockMvc, RBAC, converter et Angular.

## Décisions structurantes

- `Ward` n'est plus considéré comme le futur référentiel organisationnel.
- organisation et géographie restent deux axes séparés ;
- aucun mapping automatique n'est réalisé depuis `wards.name`, `users.department` ou `users.specialty` ;
- aucune rétrocompatibilité finale par saisie libre n'est ajoutée ;
- le type historique `HospitalServiceType` n'est pas réutilisé comme identité unique du nouveau service, car un service peut porter plusieurs capacités fonctionnelles ;
- les capacités, espaces et rattachements géographiques seront traités par HOS-LOC-001-A (#131).
