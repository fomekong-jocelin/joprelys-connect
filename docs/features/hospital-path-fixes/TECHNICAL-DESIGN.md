# Conception — Corrections hospitalières
Spring Boot/Maven + Angular 22/Tailwind v4. Contrôleurs readonly sous /api/hospitalizations/placement-options, /placement-beds et /admission-visits/{patientId}. Services applicatifs : scope courant explicitement tenant, réutilisation des lectures spatiales ; projections minimales praticien et visite ; aucun droit USER_MANAGE/SPATIAL_CONFIGURATION_MANAGE accordé au professionnel.
Angular : client hospitalier readonly ; les clients de configuration demeurent réservés aux écrans de configuration. Extraction des composants consentements et CRO, gestion explicite loading/error/submit/retry.
Concurrence : VisitRepository.findByIdForUpdate dans prise en charge, libération et sauvegarde consultation, transaction service ; même verrou que les traitements IA existants. Pas de nouvelle migration.
Médicament : HospitalizationMedicationUseCase / Policy ; listes d'options par jointures et tenant explicites. Lors de l'écriture, verrou du séjour et des prescriptions du patient en ordre stable ; statut/expiration relus avant insertion, nom issu de la prescription. Les anciennes traces ne sont pas réécrites ; aucune FK nouvelle ne rend invalides les données historiques. Exceptions 400/409 génériques, sans identité d'un autre patient.
Précalcul : erreurs de sources propagées vers gestion centrale, suppression des catch génériques ; seule erreur de format quantité libre possède un fallback documenté.
Contrats dédiés HospitalizationPlacementUseCase / QueryService et DTO minimaux ; controllers de délégation. Les nouvelles lectures sont additives (MINOR seules), mais prescriptionItemId obligatoire rompt le contrat d'administration : MAJOR candidat pour une livraison du lot selon le standard SemVer. Aucune version/release préparée. Configuration conservée, aucune base locale applicative modifiée par la validation ; tests sur H2 isolé.

La comparaison expectedUpdatedAt reste rétrocompatible et optionnelle. Le verrou commun sérialise les écritures ; les clients doivent fournir ce timestamp pour que le serveur refuse une révision périmée. Close/cancel/correct utilisent également le verrou visite. Les options de placement ne constituent pas une réservation : disponibilité toujours revalidée par le backend d'admission/transfert.
